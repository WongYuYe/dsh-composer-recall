# open-pokemon-claw 页面结构草图说明

## 1. 设计目标

页面需要支持三件事：
- 一眼感知当前系统状态
- 快速理解当前任务与异常
- 在必要时完成最小控制闭环

因此页面结构建议采用：

- 左侧 / 主区：地图与场景
- 右侧 / 信息区：任务、系统摘要、时间线、动作

---

## 3. 各区域职责

## 3.1 Top Bar
职责：快速表达系统总状态

建议内容：
- 产品名 / 系统名
- 在线 / 离线
- 当前 mode
- alert level
- 最近更新时间
- 当前连接状态（HTTP / WS）

原则：
- 精简
- 永远固定
- 只放最高层摘要

---

## 3.2 地图场景区
职责：把系统状态具象化

建议元素：
- 当前 room / zone 背景
- 角色位置
- 空间动画（低频）
- 报警视觉层（灯光/色温/闪烁）

建议映射：
- work → 办公 / 工作状态
- rest + room → 室内待机 / 休息
- rest + outdoor → 室外闲置 / 巡航
- alarm → 警报控制室 / 异常聚焦

地图区不负责承载过多文字，它主要负责：
- 情绪
- 氛围
- 状态第一印象

---

## 3.3 当前任务卡
职责：页面最重要的信息块

建议字段：
- 当前任务标题
- 任务状态
- 进度条
- startedAt / ETA
- failureReason / lastError
- nextTask
- 可执行动作

视觉优先级：
- 高于摘要卡
- 高于日志
- 必须让用户 3 秒内读懂

如果没有任务：
- 明确显示“待机 / 空闲 / 等待任务安排”
- 不要只留空白

---

## 3.4 系统摘要卡
职责：帮助理解当前整体局面

建议字段：
- queue: queued / running / failed
- sessions count
- gateway health
- refresh status
- ws clients / last event id（可选）

原则：
- 用于“理解局面”
- 不抢当前任务卡主位
- 尽量结构化、固定化

---

## 3.5 事件时间线
职责：告诉用户“刚刚发生了什么”

建议事件类型：
- 状态事件
- 任务事件
- 异常事件
- 人工动作事件

建议样式：
- 状态事件：中性
- 任务事件：主色
- 异常事件：警示色
- 成功动作：成功色

原则：
- 不要塞原始日志
- 要读得快
- 每条事件都应该是一句可读摘要

---

## 4. 状态语义重构建议

建议明确分成两个维度：

### 4.1 行为态
- rest
- work
- handling
- waiting
- blocked

### 4.2 健康态
- green
- amber
- red

这样 UI 上可以同时表达：
- 系统正在工作
- 但当前健康态是 amber

而不是所有语义都挤进一个状态字段。

---

## 5. 交互原则

### 5.1 默认“观察”，不是“操作”
用户大多数时间应该只是在看。

### 5.2 动作少而关键
保留：
- retry
- resolve
- agent turn

避免：
- 大量配置表单
- 复杂管理项
- 多层菜单

### 5.3 异常时给出明确 CTA
当进入 alarm：
- 为什么 alarm
- 是否阻塞
- 可以怎么处理
必须一目了然。

---

## 6. 视觉节奏建议

### 正常态
- 动画低频
- 颜色稳定
- 信息稀疏但清晰

### 忙碌态
- 地图活动感增强
- 当前任务卡强调进行中

### 异常态
- 提高对比
- 强化原因说明
- 避免过度闪烁造成疲劳

---

## 7. 下一步建议落地顺序

### 第一阶段
1. 当前任务卡升主位
2. 系统摘要卡固定结构
3. 时间线替代原始日志堆叠
4. 行为态 / 健康态分离

### 第二阶段
5. alarm 进入条件与异常文案重构
6. 动作区视觉与交互收敛
7. nextTask 呈现优化

### 第三阶段
8. 场景动画强化
9. 空闲 / 工作 / 报警的氛围差异增强
10. 大屏 / 第二屏使用体验优化
